## 1. Current State — What Actually Exists

**Task/goal (from the presentation):** detect brain tumors on axial/coronal/sagittal MRI slices using a dual-model approach — YOLOv5 for speed, Faster R-CNN for accuracy — reporting tumor location, bounding box and "percentage of tumor." Reported accuracy: YOLOv5 98.3%, Faster R-CNN 92.6%, thresholding/Otsu baselines ~77–84%. Status per the team's own roadmap: models trained, **web UI still "in progress,"** documentation not started.

**Repo contents:**
- A **YOLOv5 (Ultralytics, older fork) full git clone** dropped into the project root, largely untouched — this is upstream code, not project code.
- `detect.py` — stock YOLOv5 `detect.py` with **hardcoded Windows absolute paths** (`C:/Users/tekir/OneDrive/Desktop/...`) baked into the default arguments, and the `--weights` default pointed at a **Faster R-CNN checkpoint** file (architecture mismatch — this script cannot run as shipped).
- `gui.py` — a Flask app that loads a YOLOv5s architecture via `torch.hub` and then calls `load_state_dict()` with the **Faster R-CNN checkpoint's weights** — this will throw immediately, the two architectures are incompatible. This is the only "web app" artifact that exists; it is non-functional.
- `yolo2xml.py`, `generate_tfrecord.py`, `pbtxtmaker.py`, `model_main_tf2.py` — one-off conversion/training scripts for the **TensorFlow 1/2 Object Detection API** path (not torchvision Faster R-CNN, despite the `.pt` extension on the checkpoint file — the "Faster R-CNN" model is a TF SavedModel/checkpoint, exported/renamed with a `.pt` suffix, which is misleading).
- `package.json` — an empty stub (`{"dependencies": {"node": "^25.3.0"}}`) — no actual frontend was ever built, despite `.angular-config.json` and `.npmrc` suggesting an abandoned Angular attempt.
- Two `.ipynb` notebooks (one duplicated in `.ipynb_checkpoints`) containing the actual experimentation — these are the closest thing to real project logic but weren't inspected line-by-line here given their size; they should be treated as the source of truth for what was actually run.
- `.condarc`, `.python_history`, `.lesshst`, `.ipython/` history DB — machine-specific junk that should never have been committed.

**Dataset (`archive/`):**
- Three parallel datasets by MRI plane: `axial_t1wce_2_class`, `coronal_t1wce_2_class`, `sagittal_t1wce_2_class` — each with `images/{train,test}` and `labels/{train,test}` in **YOLO `.txt` format**, plus a per-plane `.yaml`. ~1,850 images, ~800 YOLO label files total (some images have no matching label — background/negative frames, which is fine, but wasn't flagged/verified anywhere in the code).
- A **second, parallel copy of the same images re-annotated as Pascal VOC `.xml`** under `training_/images/{train,val}`, generated by `yolo2xml.py` for the TF Object Detection pipeline. This is a legitimate need (YOLO and TF-OD want different label formats) but it means **any relabeling has to happen in two places by hand** — nothing keeps the `.txt` and `.xml` versions in sync.
- `training_/annotations/` — TFRecord files (`train.record`, `val.record`) and a `label_map.pbtxt` — compiled artifacts of the XML labels, now stale/derived data sitting in version control.
- `training_/demo_model/` and `training_/model/` — **two full copies of a Faster R-CNN TF checkpoint** (ResNet101 backbone, COCO-pretrained, `faster_rcnn_resnet101_v1_640x640_coco17_tpu-8`), including `saved_model/variables/` weights, TensorBoard event files, and a `pipeline.config`. This is ~80–100 MB of binary checkpoint duplicated across two folders for no clear reason.
- `tumor/outputs/my_experiment` through `my_experiment39` — **40 near-empty duplicate experiment-output folders**, almost certainly created by re-running a training/demo script without `--exist-ok` or a run-name scheme, and never cleaned up.
- A top-level `New`, `New (1)`, `New (2)`... series of ~230 duplicate-named entries — looks like repeated "Save As" / re-export artifacts from a labeling tool, never deduplicated.
- `outputs/my_experiment/`, `test/`, `train/`, `val/` at the archive root — extra copies/partial mirrors of the same data, purpose unclear without opening them.

**Models actually present:**
- `yolov5s.pt` — stock pretrained YOLOv5s COCO weights (14.8 MB) — i.e., the **base pretrained model, not a fine-tuned tumor detector**. There is no `best.pt`/`last.pt` from an actual training run anywhere in the archive.
- `faster_rcnn_resnet101_v1_640x640_coco17_tpu-8.pt` / `tumor_detector_axial.pt` (42 MB each, identical size — likely the same file saved twice) — these are named `.pt` but the accompanying `training_/model/` directory shows this is really a **TensorFlow checkpoint** (`ckpt-N.index` / `.data-00000-of-00001` + `saved_model.pb`), not a PyTorch state dict. Whatever process produced the `.pt`-named files needs to be reverse-engineered from the notebook before assuming they're usable in PyTorch — as shipped, `gui.py`'s attempt to load them into a PyTorch YOLOv5 model is the direct proof this is broken.

**Presentation vs. repo mismatch:** the slides report finished quantitative results (98.3%/92.6% accuracy, loss curves, thresholding comparisons) and a working combined-model demo, but the delivered code cannot reproduce any of it end-to-end — the inference scripts don't run as shipped, and no fine-tuned PyTorch weights exist in the archive. The real results almost certainly live only inside the two Colab notebooks.

## 2. Problems Found (Ranked)

1. **Both inference entry points are broken as shipped.** `gui.py` loads mismatched model/architecture and will crash on the first request. `detect.py` defaults to a Windows path that doesn't exist and to a weights file with the wrong architecture for the script.
2. **No portable, reproducible model artifact.** The only fine-tuned weights (if they exist at all) are TensorFlow checkpoints; the PyTorch side only has stock pretrained YOLOv5s. There is nothing here you can `torch.load()` today and get tumor predictions from.
3. **Hardcoded local machine paths throughout** (`C:\Users\tekir\...`) in `detect.py`, `gui.py`, `yolo2xml.py` — none of this runs on another machine without manual edits.
4. **Dataset duplication and drift risk.** YOLO `.txt` and Pascal VOC `.xml` labels for the same images live in separate trees with no linkage/versioning; if one is corrected, the other silently goes stale.
5. **~40 duplicate experiment-output directories and ~230 "New"-named duplicate files** — dead weight, no retention policy, makes it impossible to tell which run produced which artifact.
6. **A full upstream `yolov5/` repo (including its own `.git/`) is vendored wholesale** instead of used as a dependency — this bloats the repo, makes updates impossible, and buries the ~6 files that are actually project-specific among hundreds of upstream files.
7. **No environment/dependency manifest.** No `requirements.txt`, no `environment.yml` — the notebook and TF-OD scripts imply a TensorFlow 1/2 Object Detection API install (notoriously version-fragile) alongside a separate PyTorch/YOLOv5 install, undocumented.
8. **No train/val/test integrity checks.** No script verifies that every image has (or intentionally lacks) a label, that boxes are within image bounds, or that class ids are consistent across the three plane datasets.
9. **Frontend was never built.** `package.json` is an empty stub; the presentation's own "Next Steps" slide confirms the web interface was not done.
10. **No evaluation harness.** The 98.3%/92.6% "accuracy" figures on the slides use plain accuracy `(TP+TN)/(TP+TN+FP+FN)` for a **detection** task — that's a classification-style metric applied to boxes, not mAP/precision/recall at IoU thresholds, which is what detection actually needs. This should be treated as unverified until re-computed properly.

## 3. What Will Be Reused

- **The three annotated MRI datasets** (axial/coronal/sagittal, YOLO format) — this is the real asset. It needs deduplication and validation, not re-labeling.
- **The project's framing and clinical outputs concept** (bounding box, confidence, tumor-area %, annotated image, downloadable report) — good scope, just needs an actual implementation.
- **The two Colab notebooks**, as the historical record of what was actually run — worth mining for hyperparameters and any real result logs before they're archived.
- **The plane-specific dataset split** (axial/coronal/sagittal) — a genuinely useful structuring idea for a clinical tool, worth carrying into the new design as a `view` metadata field rather than three separate models.

## 4. What Will Be Rewritten

- Both inference paths (`detect.py`, `gui.py`) — replaced entirely with modern Ultralytics API calls (see below), no vendored `yolov5/` repo.
- The TF Object Detection API / Faster R-CNN training path — replaced (see Model Strategy) rather than resurrected, given the tooling is effectively unmaintained and the checkpoint that exists is TF, not the PyTorch/torchvision assumption the rest of the project needs.
- Label pipeline — single source of truth (YOLO `.txt`), with export scripts to other formats generated on demand instead of stored as duplicate trees.
- All hardcoded paths — replaced with a `config.yaml` + environment variables.
- Everything web-related — built from scratch (FastAPI backend, Next.js frontend), since nothing usable exists today.

## 5. Model Strategy (Task 5)

Recommendation: **drop the dual YOLO+Faster R-CNN approach and standardize on a single modern one-stage detector — Ultralytics YOLOv11** — rather than resurrecting Faster R-CNN.

Reasoning:
- The presentation's own numbers (YOLOv5 98.3% vs. Faster R-CNN 92.6%, on a flawed accuracy metric, but directionally consistent with the literature) already show YOLO ahead on this dataset.
- A tumor bounding box on a single 2D MRI slice is a **single-class, single/few-instance-per-image** problem — exactly where two-stage detectors' main advantage (small/dense/crowded object recall) doesn't pay for its cost. Faster R-CNN's main selling point doesn't apply here.
- Two-stage detectors roughly double engineering surface area (two training pipelines, two label formats, two serving paths, two sets of failure modes) for a problem that doesn't need it.
- If recall on subtle/small tumors becomes the bottleneck after a real YOLOv11 baseline, **RT-DETR** (also in the Ultralytics ecosystem, same data format, no separate TF stack) is a better escalation path than Faster R-CNN — transformer-based detectors close most of the accuracy gap to two-stage detectors without a second toolchain.
- This also directly fixes problem #7 (no more parallel TF Object Detection API install) and #4 (one label format, one pipeline).

If a stakeholder specifically wants the "dual model" story preserved for presentation purposes, the fallback is YOLOv11 (primary) + RT-DETR (secondary, same PyTorch/Ultralytics stack) — still one dependency stack, still one label format, but keeps a two-model comparison narrative.

## 7. Technology Choices

| Layer | Choice | Why |
|---|---|---|
| Detection model | Ultralytics YOLOv11 | Single stack, best speed/accuracy tradeoff for this data, active maintenance (see Model Strategy) |
| Training/inference | PyTorch + torchvision | Free, standard, GPU-optional |
| Backend | FastAPI + Uvicorn | Free, async, auto-generated OpenAPI docs, easy to pair with a PyTorch model in-process |
| Frontend | Next.js + Tailwind + shadcn/ui | Free, matches the original intent, fast to build a clean upload/report UI |
| Experiment tracking | MLflow (local) or TensorBoard | Free, no account/API key required (W&B free tier requires an account; kept optional) |
| Storage | Local filesystem, SQLite by default / Postgres optional | Zero-config to start, upgrade path if needed |
| Deployment | Docker + docker-compose | Reproducible, works identically on the free hosts listed (HF Spaces, Render/Railway free tiers, local) |

## 8. Constraints Observed From This Environment

This audit and plan were produced in a sandboxed analysis environment with **no GPU, 1 CPU core, ~4 GB RAM, and network access limited to package registries (PyPI/npm/GitHub)** — not Kaggle, TCIA, or general internet. That means:
- I can write and smoke-test the modernized training/inference/backend code here, but **cannot actually run a real YOLOv11 fine-tuning job** (needs GPU + hours) or **cannot re-download the dataset from Kaggle** (already have it from your upload).
- Anything requiring a live browser session (deploying to a real cloud host, testing the Next.js UI in a real browser) can be scaffolded here but should be run/verified on your machine or CI.

1. **ML core** — cleaned dataset config, `train.py`/`predict.py`/`evaluate.py`/`export.py` for YOLOv11, `config.yaml`, `requirements.txt` — runnable by you locally or on Colab/Kaggle free GPUs.

3. **Frontend** — Next.js upload/detect/report UI.
